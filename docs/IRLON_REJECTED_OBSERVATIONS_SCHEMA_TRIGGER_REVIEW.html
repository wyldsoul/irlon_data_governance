IRLON Rejected Observations
Schema & Trigger Architecture Review

Technical/design review of a generic public-parameter rejection registry and its first concrete SBE37 enforcement module.

Pilot / design review — not deployed to production

Purpose

A deliberate rejection makes the affected public parameter value NULL; it does not delete or NULL the private/raw observation. The central registry records why the public parameter was suppressed, including the applicable QC rollup and audit metadata. Active records prevent later ingestion or replay from silently restoring that rejected value. Suppression is parameter-level, not whole-row deletion.

1. Generic IRLON governance registry

The registry is intended for all governed IRLON public tables. The fields below are the current rejected_observations schema.

2. Active rejection identity and uniqueness

Only active records participate in uniqueness, so a reinstated decision remains in history without blocking a later active decision. Every active identity includes its required instrument serial:

Active rejection identity

source_table, public_table, source_station, public_station, instrument_type, instrument_serial, m_date, public_parameter.

A missing source serial is incomplete data, not a serial-less identity.

CREATE UNIQUE INDEX rejected_observations_active_parameter_key
ON rejected_observations
  (source_table, public_table, source_station, public_station,
   instrument_type, instrument_serial, m_date, public_parameter)
WHERE active;

3. QC flag

IRLON QARTOD rollup convention
1 = bad   2 = suspect   3 = good
The registry stores the applicable existing IRLON QARTOD rollup; it does not create a separate rejection-specific QC vocabulary. 
qc_flag integer NOT NULL CHECK (qc_flag IN (1, 2, 3))

Enforcement remains instrument/table-specific because source identity, private→public station mapping, valid public parameters, and replay/write behavior differ. The shared registry avoids repeating rejection/audit storage, while the implementation avoids one giant dynamic trigger that mutates arbitrary public columns.

5. Current SBE37 trigger example

Public write guard

sbe37_guard_rejected_public_parameters
BEFORE INSERT OR UPDATE on seabird_sbeeco

Runs through sbe37_guard_public_parameter_write() for the SBE37/ECO public path. It returns immediately when no active SBE37 rejection applies. Otherwise it requires transaction-local private identity, validates private station → public station mapping, and confirms the private station + seabird_sbe37.serial_number_sbe37 + timestamp observation exists.

Matching rejected parameter(s) are forced to NULL and their paired public QC column receives the stored qc_flag. Missing, mismatched, or fabricated identity fails closed; unrelated parameters remain writable.

Private replay reapplication

sbe37_reapply_rejected_public_parameters
AFTER INSERT OR UPDATE on seabird_sbe37

Runs through sbe37_reapply_rejections_after_private_write(). It does nothing when no exact active SBE37 rejection exists. For a match, it re-applies NULL + stored QC suppression to the mapped public parameter(s).

It never NULLs or deletes private/raw SBE37 data.
